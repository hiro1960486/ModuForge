# ModuForge アプリ開発思想・基本原則 (Draft v0.1)

> **位置づけ:** ModuForge、FileWorkbench Next、Industrial I/O、および将来のモジュール型アプリ開発の共通設計理念。2026-10-12議論に基づく提案。未承認のDraftであり、既存製品の実装状況や安全認証を表さない。

## 一丁目一番地

**安全を最優先に、既存の資産を最大限活用し、必要最小限の変更で柔軟に拡張できるシステムを作る。**

### 1. Safety First — 安全要求を最上位に

- 危険操作を特定し、要求仕様・リスク評価から設計する。
- 監視と制御、閲覧と変更、能力と許可を明確に分離する。
- 制御機能は初期状態で無効（Default Deny）。必要権限、対象、状態、最終確認、記録を満たす場合のみ実行する。
- 非常停止や人身・設備保護に必要な安全機能は、汎用アプリや通信に依存せず、適切な設備側の安全機構で実現する。
- 故障・停電・通信断で安全を保証する手段は対象ごとのリスク評価で決定し、すべての機器が通信断で停止すると想定しない。

### 2. Verify Actual State — 指令・応答・実動作を区別

- 「送信完了」「機器応答」「動作確認」を別の状態として記録する。
- センサー情報に加え、取得可能ならコイル電圧、負荷電流、補助接点、PLC内部信号などから実状態を照合する。
- 状態照合エンジンは、期待状態・観測状態・取得時刻・データ品質・動作遅延を統合して、不一致や不明を示す。
- 観測点の不足や故障検出限界を明示し、推定を実証と取り違えない。

### 3. Evidence and Quality — データの根拠・鮮度

- 共通取得レコードの基本項目は `device_id`, `point_id`, `value`, `unit`, `timestamp`, `quality`。
- `GOOD`, `STALE`, `BAD`, `UNKNOWN` などの状態を区別し、古い情報や通信異常を正常表示しない。
- 値、実測、推定、診断結果を区別し、可能なら取得経路・機器ID・時刻を追跡可能にする。

### 4. Retrofit First — 既設資産優先・最小改修

1. 既存PLC、計測器、通信プロトコル、接点、ログなどのデータ取得可能性を確認。
2. 不足する観測点は簡易I/F、絶縁入力、通信ゲートウェイ等で補完可能か検討。
3. それでも不可欠な場合にのみ、物理センサー追加・設備改修を提案。
4. 改修費のほか停止時間・工事・再検証・保守負荷を評価。
5. **安全上必須の機構をコスト削減目的で省略しない。**

### 5. Modular & Open Interface — メーカーに依存しない拡張

- 機器固有の通信処理はアダプターモジュールへ隔離する。
- 共通APIと共通データモデルを上位UI・記録・診断・警報へ提供する。
- `read` / `verify` / `control` の能力をモジュールごとに宣言。能力と現在の制御許可を別々に管理。
- メーカー固有APIが安全ポリシーを迂回できない構造にする。
- 各モジュールの単体試験を可能にし、模擬機器・Developerモード・異常系試験を優先する。

### 6. Traceability — 変更と結果を記録

- 操作者、日時、対象、意図、指令、応答、実状態、失敗／不明を記録。
- 危険操作に確認・承認・ロールバック／復旧手順を設ける。
- 文書は「計画・未実装・検証済み」を混同せず、試験根拠を残す。

## 汎用アプリへの適用例

| 対象 | 読み取り・観測 | 変更・制御 | 実状態の照合 |
| --- | --- | --- | --- |
| Industrial I/O | センサー、PLC、電力 | 接点、設定変更 | 接点、電流、位置など |
| FileWorkbench Next | スキャン・検索・比較 | 移動、削除、リネーム | 対象パス、内容、結果の検証 |
| その他モジュール | データ参照・解析 | 永続データ変更・外部操作 | 結果・ログ・整合性の確認 |

## 推奨設計レビュー項目

- [ ] 危険操作と必要な安全要求が明示されている
- [ ] 読み取りと変更の権限が分離されている
- [ ] 許可されない操作は標準状態で拒否される
- [ ] 指令成功と実動作成功を混同しない
- [ ] データ品質と鮮度を評価する
- [ ] ハード変更前に既設情報の活用を検討する
- [ ] 共通API／アダプターの責務境界が明確である
- [ ] 異常系・通信断・復旧試験と監査ログがある
